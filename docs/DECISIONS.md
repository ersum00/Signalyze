# Decisions

Short, dated records of choices that are not obvious from the code. Newest last.

## 2026-09-12 · Server layout: Docker + shared Caddy edge, not host nginx + certbot

**Context.** The brief assumed a host nginx, certbot and a host PostgreSQL on 62.238.97.127.
A read-only inspection showed a different, consistent pattern already used by the other
projects there: every project is its own Docker Compose stack with its own `postgres:16-alpine`
container on a private network, and a single Caddy container (`koradar-caddy`) owns ports 80/443,
issues certificates automatically and reverse-proxies to containers on the shared `web-proxy`
network. There is no host nginx, no certbot, no host PostgreSQL and no `uv` on the host.

**Decision.** Follow the existing server pattern exactly rather than introduce a second edge:

- `deploy/docker-compose.yml`: `signalyze-db` (own Postgres, small memory limits),
  `signalyze-api` (uvicorn, 2 workers) and `signalyze-web` (nginx serving the static landing).
- `deploy/caddy/signalyze.caddy`: a marker-delimited block that `deploy/deploy.sh` appends to the
  shared Caddyfile, validates, and reloads gracefully (with backup and automatic rollback).
- The brief's `deploy/nginx/signalyze.conf` and `deploy/systemd/signalyze-api.service` are kept
  verbatim as the documented bare-metal alternative; `deploy.sh` refuses to run if the Caddy edge
  is absent and points to that section of `docs/DEPLOY.md`.
- "Use the existing PostgreSQL" is satisfied in spirit: there is no shared instance to reuse, and
  attaching to another project's database container would couple Signalyze to that project's
  lifecycle (a `docker compose down -v` there would delete our data). A dedicated container costs
  roughly 30 MB of RAM.

**Caveat.** The shared Caddyfile belongs to the `kopiyasa` repository whose deploy does
`git reset --hard`. That would remove our block; re-running `deploy.sh` restores it. The block
should also be added to that repository (owner's call; we never modify other projects).

## 2026-09-12 · Two implementations of the signal engine, one set of fixtures

The engine must run in the extension (offline fallback, TypeScript) and on the server (Python).
Rather than running Node on the server, the Python port mirrors the TypeScript reference
function-for-function. Both test suites load the same JSON fixtures under
`packages/signals/fixtures/` (synthetic datasets + expected outputs generated by the TypeScript
engine), and the Python suite asserts equality within 1e-9. Any change to a signal must update the
fixtures, which makes divergence a test failure rather than a silent drift.

## 2026-09-12 · Forbidden words are a JSON list shared by every checker

`packages/shared/forbidden-words.json` is the single source of truth. Each entry is a regex
fragment valid in both JavaScript and Python. Word boundaries are Unicode-aware so Turkish, German
and Spanish forms are caught, while unrelated words that merely contain a term (for example a
robot vacuum) are not. The CI script scans i18n, docs, landing, extension source, engine source,
API source and deploy files. Tests and fixtures are excluded because they must contain the terms as
negative examples.

## 2026-09-12 · Extension id pinned with a committed public key

`apps/extension/extension-key.json` holds the RSA public key that Chrome uses to derive the
extension id, so every unpacked dev build gets the same id and the API's CORS list can be fixed.
The matching private key is generated locally into `apps/extension/keys/` and gitignored; it is not
needed for anything (Chrome Web Store signs uploads itself). After the first Store upload the Store
public key replaces the dev key and the Store id is added to `EXTENSION_IDS`.

## 2026-09-12 · DOM access is confined to one folder, enforced twice

All Google-layout-dependent code lives in `apps/extension/src/adapters/google-maps/`. An ESLint
`no-restricted-syntax` rule forbids `querySelector`-style calls elsewhere, and
`scripts/check-dom-isolation.mjs` repeats the check on raw text in CI so a lint-config mistake
cannot silently reopen the door.

## 2026-09-12 · Workspace packages are consumed as TypeScript source

`@signalyze/shared` and `@signalyze/signals` export `./src/index.ts` directly. WXT, Astro and
Vitest all bundle TypeScript, so a build step for the packages would only add a way to run stale
code. `tsc --noEmit` per package is the type gate.

## 2026-09-12 · Score is a renormalised weighted mean, calibrated on Google-shaped baselines

A single unusual signal can raise the score by at most its weight share (a pure 60% burst lands
around 25, not 90). This keeps the number explainable ("which signals, how much") and avoids the
impression of a verdict. Calibration points in `packages/signals/data/thresholds.json` start where
typical Google Maps places sit: rating-only reviews and templated owner replies are common, so
`no_photo_short_text` and `owner_response_pattern` only count at very high shares, and rating
polarity starts at 82% because Google ratings are 5-star heavy. The synthetic "normal" dataset was
adjusted to behave like a typical place (a quarter of reviewers with one review, low ratings paired
with negative texts, varied owner replies) so that it scores near zero; it is a test fixture, not a
claim about real baselines. Revisions bump the engine version and are logged in the changelog.

## 2026-09-12 · `!` is the accepted acknowledgement for checked index access

`noUncheckedIndexedAccess` is on. typescript-eslint's strict and stylistic presets contradict each
other on how to narrow an index access (`as T` vs `!`); `no-non-null-assertion` is turned off and
the stylistic `!` form is used only after an explicit bounds check.

## 2026-09-12 · Adapter fixtures: one real capture, three derived language variants

Google now serves signed-out browser sessions a "limited view" of a place (five reviews, no
paging, often no Reviews tab) after the first successful page load, and repeats it for a while
even from fresh profiles. One real capture succeeded (Pera Museum, Istanbul, 40 reviews, `hl=en`,
anonymised) and is the regression fixture. The Turkish, German and Spanish fixtures are that same
DOM with Google's UI strings rewritten, marked `synthetic: true` in their meta files; they cover
the date, star-label and count parsers in those languages but not real layout variations. The
capture script and the exact commands to re-run real captures are in the adapter folder and in
the README; re-capturing is a manual, headed-browser task.
